ARCHITECTURE & DEVELOPMENT PLAN
Closed-Loop Natural-Pigment DSSC Discovery Platform
=====================================================

Planning only. No code, no scaffolding, no git init yet. Where the original
spec had a weak assumption, it is flagged and an alternative proposed —
clearly marked so it can be overruled.

=====================================================
A. SYSTEM UNDERSTANDING
=====================================================

The actual contribution here is NOT "an ML dashboard for solar cells." It's a
provenance-preserving experimental design system: a database and software
architecture that lets a small (~70-85 condition), expensive, slow-to-generate
dataset be used safely for both scientific inference (papers 1-3) and
sequential decision-making (papers 4-6), without those two uses contaminating
each other.

The hard problem is not "train a regressor for PCE." It's:

1. Keeping raw measurement, derived descriptor, experimental condition, and
   device replicate as distinct, traceable entities so that a 3-replicate
   small-N dataset doesn't silently leak across train/test splits.
2. Making the Bayesian optimizer's recommendations auditable — every proposed
   experiment must be reconstructable from a specific model version, dataset
   snapshot, and acquisition function state.
3. Treating synthetic data (needed to test the closed loop before risking
   real lab time) as radioactive — clearly separated from real data at the
   schema level, not just by convention.
4. Accepting that N≈70-85 is small enough that naive use of RF/XGBoost + SHAP
   will produce confident-looking nonsense unless CV, feature count, and
   grouping are all disciplined from day one.

So: this is a data-integrity and decision-provenance system first, with
ML/BO as consumers of that system, and a dashboard as the last, thinnest
layer.

=====================================================
B. SCIENTIFIC WORKFLOW
=====================================================

[Plant Collection/Authentication]
        |
[Pigment Extraction]  --solvent, ratio, pH, T, t--> PigmentExtractBatch
        |
[Chemical Characterization]  (FTIR, HPLC/LC-MS)  --> RawSpectrum --> DerivedDescriptor
[Optical Characterization]   (UV-Vis)             --> RawSpectrum --> DerivedDescriptor (lambda_max, bandwidth, integrated absorption)
        |
[Photoanode Fabrication]  (TiO2 thickness, sintering) --> PhotoanodeFabricationBatch
        |
[Sensitization]  (adsorption time, dye loading, T) ----> SensitizationRun
        |
[Device Assembly]  --> Device (replicate N of ExperimentalCondition C)
        |
[Electrochemical/EIS]  --> RawSpectrum(EIS) --> DerivedDescriptor (Rs, Rct, Rrec, tau_e)
[Photovoltaic J-V]     --> RawCurve(JV)     --> PhotovoltaicMeasurement (Voc, Jsc, FF, PCE)
[Stability/Ageing]     --> repeated PhotovoltaicMeasurement over time --> StabilityMeasurement (retention %)
        |
[Data Validation]  (units, physical bounds, duplicates, provenance completeness)
        |
[MLDataset assembly]  (versioned, feature set, group keys for leakage-safe CV)
        |
[ML Training + Evaluation]  (baselines, nested/grouped CV, uncertainty)
        |
[SHAP / XAI]  (global + local, association only)
        |
[Bayesian Optimization]  (GP surrogate, constrained mixed search space, acquisition)
        |
[Recommendation]  PROPOSED -> APPROVED (human) -> back to top of loop as a new ExperimentalCondition

Every box on the top half (plant -> PV/stability measurement) is wet-lab,
human-paced. Everything from "Data Validation" down is software, this
project's actual scope. The loop closes at "APPROVED", which re-enters the
top half — the software never fabricates anything itself.

=====================================================
C. REQUIREMENTS ANALYSIS
=====================================================

ESSENTIAL (blocks any scientific claim)
- Domain models + relational schema distinguishing condition/replicate/
  measurement/derived-descriptor, with full provenance columns.
- Data validation layer (physical bounds, unit consistency, duplicate
  detection, no silent zero-fill).
- Raw-data immutability + traceable derived descriptors.
- Leakage-safe ML evaluation (grouped/nested CV, baselines, documented A/B/C
  validation strategies).
- Reproducibility ledger (dataset version, feature set version, model run,
  seed, code version).
- SHAP-based XAI with explicit "association != causation" labeling in every
  output.
- Single-objective (PCE) BO with a constrained, mixed-type search space, per
  species.
- Closed-loop state machine with an explicit human-approval gate.
- A synthetic-objective closed-loop test that exercises the entire pipeline
  before any real recommendation is trusted.

DESIRABLE (strengthens papers, not blocking)
- Multi-objective (PCE + stability) Pareto optimization.
- Cross-species leave-one-out generalization study.
- Automated raw-spectrum -> descriptor pipelines (auto lambda_max extraction,
  EIS equivalent-circuit fitting).
- Streamlit research dashboard.
- Automated report/figure generation for manuscripts.

FUTURE/ADVANCED (do not build now, may never be needed)
- Deep learning of any kind — explicitly rejected at this N; revisit only if
  N grows past ~300-500 with strong regularization justification.
- Batch/parallel BO (proposing >1 experiment per cycle with diversity
  constraints) — only worth it if lab throughput actually supports parallel
  fabrication.
- LIMS/instrument-direct integration, multi-lab federation, active-learning
  beyond standard BO.

        Reports/Figures  -+--> depends on --> Application/Orchestration (closed_loop)
        Notebooks        -+                              |

Rules that make this real, not aspirational:
- Domain layer = Pydantic models representing scientific entities
  (ExperimentalCondition, Device, Measurement, etc.). Zero imports from
  SQLAlchemy, scikit-learn, or Streamlit. These double as the data contracts
  in Section G.
- ML/BO packages import only numpy/pandas/domain models — never sqlalchemy,
  never streamlit. This is what lets you literally run
  `python scripts/run_bo_cycle.py` from a terminal, which the spec requires
  (section 10).
- Repository pattern sits between SQLAlchemy ORM rows and domain Pydantic
  objects — DB schema can evolve without ML code noticing.
- Streamlit pages are read-only consumers of application-layer functions; no
  business logic lives in ui/.

=====================================================
E. DATABASE DESIGN
=====================================================

The single most important correction to the originally proposed schema: it
lists categories of information (extraction, chemical, optical, ...) but not
the entities that carry them. Flattening everything onto one "pigment"
record is exactly the leakage risk the spec asked to guard against. Here's
the entity model:

Entity                          | Grain                          | Key relationships
---------------------------------------------------------------------------------------
Species                         | one per taxon                  | reference table
PlantSample                     | one collection event/voucher   | -> Species
PigmentExtractBatch             | one extraction run             | -> PlantSample; solvent/pH/T/t/yield
RawSpectrum                     | one instrument acquisition     | -> PigmentExtractBatch or -> Device (polymorphic source)
                                 | (UV-Vis/FTIR/HPLC/LC-MS/EIS/JV)|
DerivedDescriptor                | one computed value             | -> RawSpectrum (source), processing_version, algorithm
PhotoanodeFabricationBatch       | one TiO2 prep run              | thickness, sintering T/t, surface treatment
SensitizationRun                 | one dye-loading process        | -> Device, -> PigmentExtractBatch; adsorption time/conc/T
ExperimentalCondition (**)       | one DoE/BO "recipe"            | -> Species; embeds/references extraction+sensitization+
                                 |                                 |    photoanode parameter vector; this is the unit BO optimizes
Device (**)                      | one physical replicate         | -> ExperimentalCondition, -> PhotoanodeFabricationBatch,
                                 |                                 |    -> SensitizationRun; replicate_number
ElectrochemicalMeasurement (EIS) | one fit result                 | -> Device, -> RawSpectrum; Rs/Rct/Rrec/tau_e, circuit model
PhotovoltaicMeasurement          | one J-V scan                   | -> Device; Voc/Jsc/FF/PCE, illumination protocol
StabilityMeasurement             | one ageing timepoint           | -> Device, -> initial PhotovoltaicMeasurement; ageing
                                 |                                 |    duration/conditions, retention %
MLDatasetVersion                 | one frozen snapshot            | query definition hash, row/condition IDs included
FeatureSetVersion                | one feature definition         | descriptor list, preprocessing pipeline spec, code hash
ModelRun                         | one training run               | -> MLDatasetVersion, -> FeatureSetVersion; mlflow_run_id,
                                 |                                 |    hyperparams, seed, metrics
BOIteration                      | one BO cycle step              | -> ModelRun (surrogate), acquisition fn, search-space version
Recommendation                   | one proposed experiment        | -> BOIteration; parameter vector, predicted objective +
                                 |                                 |    uncertainty, acquisition value, state
ClosedLoopStateLog                | audit trail                    | -> Recommendation; state transitions with timestamp/operator
ValidationResult                  | outcome linkage                | -> Recommendation, -> resulting ExperimentalCondition/
                                 |                                 |    measurements; predicted-vs-actual

Why ExperimentalCondition vs Device matters concretely: the original spec
already flagged (section 13) "~3 replicates per condition" — this schema is
what makes that distinction load-bearing rather than cosmetic. All grouped CV
(Section H) groups on experimental_condition_id, never on raw row. All BO
recommendations ARE an ExperimentalCondition before any Device exists.

Identifiers: every table gets a surrogate integer/UUID PK plus a
human-readable code (e.g. BV-COND-014, TO-DEV-003-R2) generated at insert
time — surrogate keys for joins, codes for lab notebooks and error messages.

Provenance columns (shared mixin, not repeated ad hoc): operator, instrument,
raw_data_reference, measurement_uncertainty, missing_value_reason,
is_synthetic (boolean, defaults False, HARD-REQUIRED True on anything from
the synthetic-objective test harness), created_at, experiment_version, notes.

Units: store canonical SI-ish units as plain floats + a units_registry.py
module documenting the canonical unit per field, with Pint used only at the
ingestion boundary (converts whatever unit was entered to canonical, then
discards the Pint quantity object). Running Pint quantities through
pandas/sklearn pipelines is friction without benefit at this scale — flagged
as a deliberate deviation from the original suggestion, low-risk either way.

=====================================================
G. DATA CONTRACTS
=====================================================

Key schemas crossing module boundaries (Pydantic, versioned):

- ExperimentalConditionVector — the object BO both reads (as a training
  point) and writes (as a recommendation): species, extraction params
  (solvent_ratio, pH, temperature_C, time_min), sensitization params
  (adsorption_time_min, concentration_mM), photoanode params
  (tio2_thickness_um, sintering_temperature_C, sintering_time_min). Explicit
  bounds and dtype (continuous/discrete/categorical) per field.
- MLDatasetRow — features (flat floats, post-canonicalization), target(s),
  group_id = experimental_condition_id, replicate_id, sample_weight
  (optional, e.g. down-weight singletons).
- ModelPrediction — point estimate, std/interval, model_run_id, explicit
  prediction_type: {interpolation, extrapolation} tag from Section H's
  validation regime.
- SHAPExplanation — feature, shap_value, base_value, model_run_id, and a
  mandatory interpretation_caveat string field (forces the "not causal"
  disclaimer to travel with the number, not just live in a README).
- BORecommendation — ExperimentalConditionVector, predicted_objective,
  predictive_uncertainty, acquisition_value, rationale_text (human-readable,
  generated from acquisition function decomposition), state.

=====================================================
H. ML METHODOLOGY
=====================================================

Preprocessing: impute -> scale -> (optional) feature-selection, built as an
UNFIT sklearn.Pipeline factory. It is fit inside each CV fold only — never
globally before splitting. This is enforced by making the evaluation harness
the only caller of .fit().

Feature budget — the concrete guardrail the original spec was missing: at
N≈70-85 conditions, a defensible ceiling is roughly N/10 features for tree
ensembles (~7-8 features), more generously N/5 (~14) for regularized
linear/GP models with a proper kernel. Feature selection must happen INSIDE
each outer CV fold, never on the full dataset first — that's leakage even
without touching the test rows' targets, because it uses their feature
values.

Validation strategy — three distinct, separately reported regimes (the spec
asked for this explicitly; here's what each answers):

Strategy               | Split                                            | Scientific question
------------------------------------------------------------------------------------------------------------
A. Interpolation        | Leave-One-Condition-Out (LOCO) CV, grouped by    | Given the explored region, how well does the model
                        | experimental_condition_id                        | reconstruct known relationships? (Primary metric — LOCO
                        |                                                    | maximizes training data at this N.)
B. New conditions        | Time-ordered split: train on DoE + BO cycle      | Does the model, as it will actually be used, generalize
   (forward extrapolation)| 1-2, test on BO cycle 3                         | to conditions it hasn't seen — the real operational test.
C. Cross-species          | Leave-one-species-out, rotated                  | Has the model learned transferable chemistry-performance
                        |                                                    | relationships or species-specific patterns? (Paper 7.)

Report all three with repeated resampling (e.g. 10x repeated LOCO where
feasible) and confidence intervals on MAE/RMSE — a single point-estimate R²
at N=70 is not defensible.

Baselines, mandatory: mean predictor, and a simple domain baseline (e.g.
linear regression on lambda_max + dye loading alone) — every "real" model
must beat both, reported side by side, always.

Models: Ridge/Lasso, Random Forest, XGBoost, Gradient Boosting, and Gaussian
Process Regression (GPyTorch) — GPR is not just for BO; run it as a
candidate predictive model too, since at this N it's often the MOST
appropriate, not a scalability risk (see Section Q).

=====================================================
I. XAI METHODOLOGY
=====================================================

SHAP wrapper picks explainer by model family: TreeExplainer for
RF/XGBoost/GBR, KernelExplainer/permutation-based for GPR/linear (dataset is
small enough that Kernel SHAP's cost is a non-issue). Outputs: global
bar/beeswarm, local waterfall for any BO-recommended condition (explain why
the surrogate favors it, distinct from the acquisition-value rationale),
dependence plots, and interaction values flagged low-confidence given N.

Hypothesis pipeline (this is the actual mechanism connecting SHAP to the lab,
not just a diagram): every notable SHAP finding gets logged as a structured
record — observation (e.g. "high dye-loading x long adsorption-time
associated with higher PCE") -> candidate_mechanism (chemistry-grounded) ->
confound_check (what else correlates with this combination in the dataset?)
-> proposed_confirmatory_experiment -> status. This log is itself a table
(HypothesisLog), not a paragraph in a notebook, so it survives into Paper 3's
discussion section with full traceability.

Every SHAP-derived artifact carries the interpretation_caveat field from
Section G. No exceptions.

=====================================================
J. BAYESIAN OPTIMIZATION METHODOLOGY
=====================================================

Search space — per species, not joint. This is a deliberate simplification
versus a fully joint species+continuous space: conditional feasibility (e.g.
concentration ranges differ by plant, some sintering/surface-treatment
combos are infeasible) is far easier to encode as N independent
bounded/constrained continuous+categorical spaces than as one space with
conditional parameters, which BoTorch doesn't natively support well.
Cross-species knowledge transfer is handled by the ML/XAI side (Section H
strategy C), not by the optimizer. If joint optimization is wanted later,
it's an additive change, not a rewrite.

- Variable types: continuous (pH, temperature, time, concentration,
  thickness) with explicit bounds; discrete (sintering time in fixed
  increments if the furnace only supports steps); categorical (solvent
  choice, surface treatment) via MixedSingleTaskGP in BoTorch.
- Constraints: linear inequality constraints (e.g. solvent ratio components
  sum to 1), and known-infeasible combination exclusion applied at
  acquisition-optimization time, not left to the GP to learn the hard way.
- Surrogate: single-task GP per objective, Matern-5/2 kernel, standardized
  outputs, log-transform of strictly-positive skewed variables (e.g.
  concentration).
- Acquisition: qLogNoisyExpectedImprovement (BoTorch's numerically stable
  log-space EI variant) as default — plain qExpectedImprovement has known
  vanishing-gradient issues in this size regime; this is a direct upgrade,
  not a stylistic choice.
- Initialization: the ~40-point initial DoE should be a constrained
  space-filling design (Latin Hypercube respecting the feasibility
  constraints above), not literally uniform random.
- Stopping/convergence: no single test — report (a) predicted-improvement
  decay across cycles, (b) plateau in best-observed PCE, (c) budget
  exhaustion (3 planned cycles). Convergence is a judgment call made with
  these three signals, documented in the BOIteration record, not automated.
- Rationale text: every Recommendation stores a generated explanation
  decomposing why: predicted mean, predictive std, and the acquisition
  value's exploration/exploitation balance in plain language.

One correction to the original stack list: Optuna is a hyperparameter-tuning
tool (inner loop for RF/XGBoost hyperparameters during Section H's nested
CV) — it is NOT the engine for the scientific closed loop. Conflating the
two would mean using the wrong uncertainty model for lab-experiment
recommendations. BoTorch/GPyTorch is the closed-loop engine; Optuna, if used
at all, stays inside model training.

=====================================================
K. CLOSED-LOOP STATE MACHINE
=====================================================

PROPOSED --approve--> APPROVED --fabricate--> FABRICATED --measure--> MEASURED
   |                     |                        |                     |
   |reject                |fail                    |fail                 |validate
   v                     v                        v                     v
REJECTED           FAILED_FABRICATION       FAILED_MEASUREMENT      VALIDATED
                                                                          |ingest
                                                                          v
                                                                     INGESTED
                                                                          |retrain
                                                                          v
                                                                   MODEL_UPDATED

Additional terminal state: SUPERSEDED — a PROPOSED recommendation
invalidated because the surrogate was retrained (new data landed) before it
was acted on; never silently discarded, always logged with the superseding
BOIteration id. Every transition writes a ClosedLoopStateLog row with
timestamp + operator — this is the audit trail that makes "the software
never fabricates anything, a human always approves" (Section D) verifiable
after the fact, not just a policy.

=====================================================
L. TESTING STRATEGY
=====================================================

Layer                | What's tested
------------------------------------------------------------------------------
Data validation        | physical bounds (PCE>=0, valid pH, FF range), unit
                        | consistency, duplicate detection, missing-value
                        | handling never silently zero-fills
Preprocessing           | pipeline fit-on-train-only, correct handling of
                        | NaN, no leakage of test-fold statistics
Feature engineering      | MLDataset assembly produces correct group_ids,
                        | versioned snapshots are immutable/reproducible
Model pipeline            | deterministic given fixed seed; metrics computed
                        | correctly against a hand-checked toy case
Leakage tests               | explicit test that shuffling replicate rows
                        | across a grouped split raises/fails; test that a
                        | model trained ignoring groups scores implausibly
                        | better than grouped CV (canary test)
BO search space              | constraint satisfaction — sampled/optimized
                        | points never violate bounds or linear constraints;
                        | categorical handling round-trips correctly
Closed-loop simulation         | full synthetic-objective loop runs
                        | end-to-end, is_synthetic=True propagates
                        | everywhere, state machine reaches MODEL_UPDATED
Database                        | migrations apply cleanly on empty DB;
                        | repository round-trips domain objects losslessly;
                        | constraints (FKs, non-null provenance) actually
                        | reject bad inserts
Reproducibility                  | given a ModelRun id, re-running with its
                        | recorded config produces bit-identical
                        | (or documented-tolerance) metrics

Synthetic closed-loop test (gate for M7): a known analytic function (e.g. a
bounded multimodal function over the same parameter dimensionality,
explicitly documented as NOT physically meaningful) stands in for "the lab."
BO proposes -> synthetic function evaluates -> result flows through
ingestion -> model retrains -> next recommendation. This must pass, with
every synthetic row flagged is_synthetic=True, before Section J's engine
ever touches real data.

=====================================================
M. REPRODUCIBILITY STRATEGY
=====================================================

Every ModelRun and BOIteration records: dataset_version_id,
feature_set_version_id, git_commit_hash (captured via gitpython at run time
— this is why git init is the literal first implementation task),
hyperparameters, random_seed, MLflow run_id, timestamp, evaluation results.
A Recommendation is fully reconstructable by joining
BOIteration -> ModelRun -> MLDatasetVersion, answering the required question
("what exact data/preprocessing/model produced this prediction") by query,
not by memory.

   mature system as originally specified — SQLAlchemy makes the actual
   engine a connection-string change, so this doesn't block anything, but
   if reusing XAMPP's MySQL to avoid installing Postgres separately is
   preferred, say so and adjust the target dialect assumptions accordingly
   (mainly JSON-column and array-type handling differ slightly).
2. Dependency manager: plain pip + venv + pyproject.toml (simplest, no
   extra tooling) vs Poetry (stricter lock files). Recommendation: plain
   pip/venv — matches "don't introduce unnecessary technologies."
3. Package name: dssc_discovery (used throughout this plan) — flag now if a
   different name is wanted, since it's threaded through every file path.
